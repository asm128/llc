This is a recovery aid for future agents. It records why `llc_log.h` must be studied before writing LLC application code. It is not a request to copy either historical version blindly.

## What went wrong in the initial implementation

- It treated LLC as a collection of types while ignoring that diagnostics and signed-result control flow are part of the architecture.
- It repeatedly decomposed one LLC operation into a local result, `failed()` branch, handwritten message, cleanup and return.
- It used direct `fprintf(stderr, ...)` for diagnostics, bypassing LLC log callbacks and their uniform source/timestamp context.
- It created raw conversion helpers such as `bytesView()` and `textView()` instead of first looking for view constructors, `LLC_CXS()`, `vcst_t` and `.cu8()`.
- It duplicated command names and descriptions across enum values, parsing branches and help text.
- It decoded a POD response with a size check plus `memcpy()` instead of using the serialization/view facilities and their cursor contract.
- It used `llc_necs()` in places where preserving or deliberately transforming the exact error deserved an explicit choice.

The problem was not that every individual line was invalid C++. The problem was that the generated code rebuilt weaker local versions of facilities LLC already owned, making the result longer, less diagnostic and less consistent.

## Representative contrasts

### Failure, cleanup and loop control

The generated server spelled out the protocol manually:

```cpp
const ::llc::err_t readResult = ::lls::pipeReadEvent(serverPipe, request);
if(::llc::failed(readResult)) {
	error_printf("Failed to read an lls request.");
	::lls::pipeServerDisconnect(serverPipe);
	continue;
}
```

The refactor recognized that this is one diagnostic/control-flow operation and used a block form so cleanup remains explicit:

```cpp
if_true_block_logf(error_printf, llc::failed(readResult = ::lls::pipeReadEvent(serverPipe, request)), {
	if_fail_e(::lls::pipeServerDisconnect(serverPipe));
	continue;
	}, "%s", "Failed to read an lls request.");
```

Lesson: use the macro vocabulary, but never lose cleanup merely to make a branch shorter.

### Views instead of local pointer adapters

The generated code added helpers around raw pointers and `strlen()`:

```cpp
sttc ::llc::vcu0_t textView(const char * text);
sttc ::llc::vcu0_t bytesView(const void * data, ::llc::u2_t byteCount);
```

The refactor used the existing representations directly:

```cpp
vcst_t{"Expected a system command event."}
appState.CommandLineArgs.Positionals[1].cu8()
```

Lesson: inspect `llc_view.h` and the source type before inventing an adapter.

### Framework output versus raw C output

The terminal used `printf()` and `fprintf(stderr, ...)` directly. That text may be readable, but it is invisible to LLC's configured output pipeline.

Prefer `always_printf()` for ordinary console text unless a more specific LLC output facility fits better. Use the corresponding LLC severity function or macro for failures and operational diagnostics. This keeps help, status and other intentional console output inside the same callback-capable framework.

If a C-standard boundary is genuinely necessary, prefer `fprintf()` with an explicit stream over implicit `printf()`, but make that choice knowingly: both bypass the LLC framework.

### Typed arguments at the final formatting boundary

Formatting requirements should not leak back through otherwise typed code. A pointer remains `T *` or `const T *` while it moves through the application; `printf_arg()` performs the conversion required by `%p` at the formatter boundary. This keeps call sites such as the following focused on evidence rather than adapter syntax:

```cpp
error_printf("range: %p to %p", view.begin(), view.end());
```

That conversion is representational and belongs to formatting. A semantic cast that reinterprets storage or deliberately changes the value's meaning must remain visible where the decision is made.

The same boundary rule applies to logging dispatch. `log_print()` and `log_write()` are the direct callback-facing operations; layers named `base_`, underscored forwarding versions and default forwarding aliases add vocabulary without adding a contract. Platform-specific preprocessing stays narrow. For example, Arduino's `F()` must see the original literal at the call site, so `log_print_F(text)` remains a macro, while the resulting flash-string output is handled by the ordinary logging functions.

Optional variadic arguments are another legitimate preprocessing concern. `LLC_VA_TAIL(...)` contains the C++20 `__VA_OPT__` comma rule and its older-target fallback so severity macros share one implementation instead of duplicating Windows and non-Windows bodies.

### Metadata instead of duplicated command knowledge

The generated terminal hard-coded command parsing and repeated the same command descriptions in help text. The refactor moved descriptions into `GDEFINE_ENUM_VALUED`, added `MAX` sentinels, indexed command/result behavior with tables and checked table sizes at compile time.

Lesson: enum metadata should be the single source of names and descriptions when the behavior is genuinely indexed by the enum. Do not create a registry for its own sake, but do not maintain parallel stringification logic either.

### Serialization instead of raw copying

The generated result handler checked `sizeof(SServiceStatus)` and then called `memcpy()`. The refactor used a byte view and `loadPOD()`, which expresses the serialization contract and advances a cursor consistently with the rest of LLC.

Lesson: use a representation-level primitive only after checking whether LLC already gives the operation a semantic name and failure contract.

## What the refactor proves—and what it does not

Commit `5b4f035` is a valuable direction-of-travel comparison, not finished reference code. The author stopped because completing a disposable skeleton was less valuable than improving the foundational facilities first.

Known signs of incompleteness in that snapshot include:

- the header changed enum value spelling while `lls_main.cpp` still uses the earlier identifiers;
- an inline note still calls for replacing `GetTickCount64()` with `llc::STimer`;
- some loop-error paths still need a deliberate cleanup/continue review;
- some terminal error output still uses `fprintf(stderr, ...)`;
- the refactor was not promoted into the tested LLC workflow.

Therefore:

- use the initial commit to recognize anti-patterns;
- use the refactor to understand the intended LLC vocabulary;
- use current, tested `llc` and `llc_test_core` sources as the authority for final code.

## Practical checklist before writing an LLC error path

- What does success/failure mean for the returned type?
- Is the condition `true`, `failed`, `zero` or `null`?
- Should the current flow log only, continue, break, return a chosen value, return failure, or throw?
- Must an exact negative result be preserved?
- What values would make the log immediately actionable?
- Is cleanup required before the control transfer?
- Which LLC output facility fits this message? Default ordinary console output to `always_printf()`.
- If raw C output is unavoidable, is the stream explicit and is bypassing the LLC framework intentional?
- Can `printf_arg()` perform a formatting-only conversion instead of repeating a cast at the call site?
- Is a macro actually recovering call-site information or syntax, or could this behavior remain in a typed function?
- Does an existing view, serialization, enum or event helper already express the operation?
